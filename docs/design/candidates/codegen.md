# Design candidates — B4 codegen escape hatch

Area: codegen (`[generate]`). Status: **candidates for taste review**, not
normative. Evidence: BACKLOG.md B4 + S4; GAPS.md of json-tui (§1), cpptrace
(§4), benchmark (§1, §3), ninja (§2), vtz (§1), cppcheck (§1). Refines the
S4 sketch (which already picked the two-tier shape); this file completes the
semantics, the corpus rewrites, the interaction analysis, and the Linux
story, and presents two coherent alternatives so the choice is real.

Scope reminder from the corpus, in one line each:

- **json-tui / cpptrace** — `configure_file` version header, pre-generated
  by `pin.sh` + `sed`; version now stated in three places.
- **benchmark** — `git describe` stamped into a per-source define; store
  strips `.git`, so in dependency mode the fallback silently mis-versions
  rev pins. The fix is lockfile *facts*, not command execution.
- **ninja** — `browse.py | inline.sh > browse_py.h` custom command
  (pre-generated by pin.sh, goes stale silently); re2c "regenerate if tool
  present, else committed output" (dodged).
- **vtz** — zic compiles a zoneinfo tree (test fixture, not a compile
  input); two generated headers are checked in and were proven
  byte-reproducible by a hand-rolled `--verify-refresh`.
- **cppcheck** — per-source transform over 71 files (tier c; deferred, see
  §6).

## 1. Shared spec elements (common to all candidates)

These pieces are candidate-independent; each candidate says how it arranges
them, not whether they exist.

### 1.1 The `${...}` interpolation vocabulary (closed)

One interpolation grammar for the whole schema, with a **closed** variable
set. v1 vocabulary:

| Variable | Value | Available |
|---|---|---|
| `${package.name}` | `[package].name` | always |
| `${package.version}` | `[package].version` verbatim | if `version` set, else hard error at parse |
| `${package.version.major/.minor/.patch}` | split on `.`; error if the component doesn't parse as an integer | same |
| `${pin.<depkey>.commit}` | resolved commit sha from CppPkg.lock | git deps |
| `${pin.<depkey>.requested}` | the human ref: `v1.9.5` for `tag:v1.9.5`, the sha for `rev:` | git deps |
| `${gen}` | the generated-output root (see 1.2) | in the positions listed below |

Rules:

- Unknown variable → **hard error** naming the closed vocabulary. Never
  empty-string substitution (that is CMake's silent-wrong behavior; the
  declarative reading must never lie).
- Escape: `$${` produces a literal `${`.
- Allowed positions are **enumerated**, not universal: `[generate.*]`
  values (`vars`, `command` argv, `stdin`), `defines` values on targets,
  `includes`/`sources` entries (only for `${gen}`), and — once B2 lands —
  test-run `args`/`cwd`/`env` values (`${gen}` for fixtures). Everywhere
  else `${` is a hard error, so the grammar cannot creep silently.
- `${pin.self.*}` is **reserved, not implemented in v1** (open question
  Q2). Semantics recorded now so the store design doesn't foreclose it:
  when a package is built as a CppPkg-native dependency, `pin.self.*`
  resolves from the consumer lockfile entry (this is what survives the
  store stripping `.git` — benchmark's trap). Root-build resolution is the
  contested part.

Why `defines` interpolation is in scope for a codegen design: benchmark's
whole need is "one string at manifest-evaluation time, attached as a
define. No files generated, no build-graph edges" (GAPS §1). Making that a
`[generate]` step would manufacture a file nobody wants; making it a
per-source flag mechanism (S1) was explicitly deferred *because* B4 covers
it. Interpolated defines are the smallest true form.

### 1.2 `${gen}`: where outputs live

- One generated root per package: `build/gen/` (`${gen}` in manifests).
  Output paths in `[generate]` are declared **relative** and resolve under
  it; `..` segments and absolute paths are hard errors, so **source-tree
  writes are refused by construction** (vtz GAPS names source-tree
  generation as the pattern to reject).
- Ninja's browse.cc does `#include "build/browse_py.h"` — literal relative
  path — so output paths are user-chosen: `output = "build/browse_py.h"`
  lands at `build/gen/build/browse_py.h` and `-I ${gen}` makes the
  upstream include line work unmodified.
- Two steps declaring overlapping output paths → hard error at plan time.
  The collision check is **case-insensitive on all platforms** (a manifest
  authored on case-insensitive macOS must not silently mean something else
  on Linux, and vice versa).

### 1.3 How generated files join targets

- **Headers** (the corpus's only compile-time need): a target lists
  `${gen}` or `${gen}/sub/dir` in `includes` (any visibility bucket).
  These are project-owned dirs and stay `-I`, not `-isystem` — B1's
  `-isystem` fix is for *imported* interfaces only.
- **Sources**: a `sources` entry may be `"${gen}/path.cpp"`. It must match
  a declared output byte-for-byte, else hard error at plan time ("no
  generate step declares this output") — never a silently missing file.
  No globbing under `${gen}` (outputs are declared; globbing them would
  re-derive what the manifest already states).
- **Edge wiring**: command steps are ninja edges; every compile unit of a
  target that references `${gen}` gets an **order-only** dependency on a
  phony `cppkg-gen` target aggregating all step outputs. After the first
  build, real header dependencies flow through the compiler depfiles
  (`-MD`), so rebuild precision is exact from build 2 onward; order-only
  covers build 1. Generated `sources` get the true edge naturally (the
  file is the edge output). This is standard ninja/CMake practice, not an
  invention.
- **Laziness**: a step runs only when some target in the *requested* build
  set (or a test being run) references `${gen}`. With B2's
  default-build-excludes-tests, a fixture-only step (vtz zoneinfo) runs
  for `cpp-pkg test` and not for `cpp-pkg build vtz` — for free, at coarse
  grain (see Q3 for per-step grain).

### 1.4 Hermeticity and error behavior (command tier)

- `command` is an **argv array**, no shell string. `stdin`/`stdout` fields
  cover pipeline-shaped tools (ninja's `inline.sh < browse.py >
  browse_py.h`). The edge is executed through a thin internal wrapper
  (`cpp-pkg gen-exec`) which:
  - runs the argv with cwd = project root, source tree treated read-only
    by contract;
  - on **Linux**: wraps in `unshare -n` (unprivileged user+net namespace —
    works out of the box on Arch) → **no network, enforced**;
  - on macOS: `sandbox-exec` deny-network profile, best-effort
    (deprecated-but-working); policy is normative on both platforms, the
    enforcement strength differs and is documented;
  - after exit 0, verifies every declared output exists (missing → hard
    error naming the step); nonzero exit → hard error with captured
    stderr; writes go to a temp path and are committed atomically,
    unchanged bytes preserve mtime (restat-friendly).
- Undeclared *reads* are not detected in v1 (input hashing is only as good
  as the declaration — same contract ninja itself has). Declared `inputs`
  are the rebuild triggers; the wrapper does not try to prove completeness.
- Host tool identity (`zic`, `sh`, `python3`) is **not** hashed in v1; the
  edge reruns on argv or input change only. CMake has the same hole;
  recorded as a cost, not hidden.
- Network is **forbidden** in tier b by contract — pinned fetch is tier d,
  deferred (§6).

### 1.5 Rebuild semantics and the config hash

- Root project: `build.ninja` regenerates every build (v0 contract), so
  template-tier outputs are re-derived each build with write-if-changed —
  staleness is impossible (kills the pin.sh silent-staleness class).
  Command-tier edges rebuild on input mtime or command-line change,
  ordinary ninja.
- Dependencies: today deps build via CMake, so `[generate]` never executes
  in the store. When B6's round-trip lands (CppPkg-native deps), the
  entire `[generate]` table folds into the config hash as: template bytes,
  post-interpolation var values, argv, and content hashes of declared
  inputs. Pin facts are already hash inputs via the lockfile. Recorded now
  so B6 doesn't have to retrofit it.

### 1.6 Template substitution semantics (tier a)

- Token syntax: `@VAR@` only (CMake's `@ONLY` mode — every corpus template
  is a `.in` file written for it). `${VAR}` inside templates is **left
  untouched** (matches `@ONLY`, avoids colliding with shell/CMake text in
  templates).
- A token `@[A-Za-z_][A-Za-z0-9_]*@` with no binding in `vars` → **hard
  error** listing the template line. (CMake substitutes empty string;
  that's how silently-broken headers ship.) Literal `@` not forming a
  token passes through (email addresses etc.).
- A `vars` entry never used by the template → warning (drift signal, e.g.
  upstream renamed the variable).
- `#cmakedefine` / `#cmakedefine01` lines → **hard error** ("not supported
  in v1") rather than passing through as broken preprocessor text. No
  corpus site needs them; Q6 asks whether to keep the error or implement.

## 2. Candidate 1 — `[generate.<name>]`, one table, two tiers (refined S4-A)

The BACKLOG sketch, completed. A package-level table of named steps; the
tier is discriminated by which key is present: `template` (tier a) or
`command` (tier b). Exactly one of the two, else hard error.

### 2.1 TOML surface

```toml
# --- tier a: pure function of manifest + lockfile; no commands -------------
[generate.version-header]
template = "src/version.hpp.in"        # @VAR@ substitution, §1.6
output   = "src/version.hpp"           # lands at ${gen}/src/version.hpp
vars     = { CMAKE_PROJECT_VERSION = "${package.version}" }

# --- tier b: declared command, emitted as a ninja edge ---------------------
[generate.browse-py-h]
command = ["sh", "src/inline.sh", "kBrowsePy"]
stdin   = "src/browse.py"              # automatically an input
stdout  = "build/browse_py.h"          # automatically an output, under ${gen}
inputs  = ["src/inline.sh"]            # everything else the command reads
# outputs = [...]                      # for tools that take output paths as
# output-dirs = [...]                  #   args; dirs get an auto stamp file

[targets.ninja]
includes = { private = ["${gen}"] }
```

Optional third mode, shared machinery (see §2.3 for why it earns its
place): **checked-in generation** — bless the pattern vtz and ninja-re2c
already use instead of fighting it.

```toml
[generate.known-zones]
command    = ["python3", "scripts/gen_known_zones.py", "data/tzdata/tzdata.zi"]
stdout     = "known_zones.h"
inputs     = ["scripts/gen_known_zones.py", "data/tzdata/tzdata.zi"]
checked-in = "include/impl/vtz/known_zones.h"   # source-tree twin
```

A `checked-in` step is **not** part of the build graph: `cpp-pkg build`
compiles the checked-in file like any source. `cpp-pkg gen` regenerates
into `${gen}` and copies over the checked-in path (the one sanctioned
source-tree write, through an explicit verb, never during build);
`cpp-pkg gen --check` regenerates and byte-diffs (CI mode — exactly vtz's
hand-rolled `--verify-refresh`, which proved this workflow in ~20 lines).

### 2.2 Field semantics and defaults

| Field | Tier | Meaning / rules |
|---|---|---|
| `template` | a | path in source tree; content hashed as an input |
| `output` | a | single relative path under `${gen}` (a template makes one file) |
| `vars` | a | string→string; values may interpolate §1.1; required for every `@VAR@` token |
| `command` | b | argv; `argv[0]` resolved via PATH or project-relative if it contains `/`; may interpolate `${gen}`, `${package.*}`, `${pin.*}` |
| `stdin` | b | optional; project-relative file; auto-appended to inputs |
| `stdout` | b | optional; relative path under `${gen}`; auto-appended to outputs |
| `inputs` | b | files the command reads (rebuild triggers); missing file at plan time → hard error naming the step (not a silent skip) |
| `outputs` / `output-dirs` | b | declared products; at least one output among `stdout`/`outputs`/`output-dirs`; dirs are wiped before the run and represented by a stamp file in the ninja graph |
| `checked-in` | b | see above; mutually exclusive with participation in the build graph |

Step names share the `[a-zA-Z0-9_-]+` charset with targets. Steps have no
ordering fields: an input of step X that is an output of step Y (a
`${gen}` path) creates the edge implicitly; cycles are a plan-time error.

### 2.3 Corpus rewrites (before → after)

**json-tui.** Before: `pin.sh` lines 18–25 (`sed
's/@CMAKE_PROJECT_VERSION@/1.4.2/' … > upstream/gen/src/version.hpp`),
version stated in pin.sh + `[package].version` + upstream CMakeLists;
manifest: `includes = { private = ["src", "gen/src"] }` on two targets.
After — pin.sh's codegen block deleted, version stated once:

```toml
[generate.version-header]
template = "src/version.hpp.in"
output   = "src/version.hpp"
vars     = { CMAKE_PROJECT_VERSION = "${package.version}" }

[targets.json-tui-lib]
includes = { private = ["src", "${gen}/src"] }   # tests target: same edit
```

**cpptrace.** Before: pin.sh three-`sed` block into `gen/include/` (source
tree pollution), `includes = { public = ["include", "gen/include"] }`.
After:

```toml
[generate.version-header]
template = "cmake/in/version-hpp.in"
output   = "include/cpptrace/version.hpp"
vars     = { CPPTRACE_VERSION_MAJOR = "${package.version.major}",
             CPPTRACE_VERSION_MINOR = "${package.version.minor}",
             CPPTRACE_VERSION_PATCH = "${package.version.patch}" }

[targets.cpptrace]
includes = { public = ["include", "${gen}/include"], private = ["src"] }
```

Note the **public** generated include — the B6 interaction (§4).

**benchmark.** Before: `'BENCHMARK_VERSION="v1.9.5"'` hardcoded private
define, drifts silently if the pin moves; upstream's `git describe` fails
inside the store (no `.git`) and silently falls back. After — no
`[generate]` step at all, interpolated define:

```toml
[targets.benchmark]
defines = { private = [ 'BENCHMARK_VERSION="v${package.version}"', ... ] }
```

One statement of the version. When benchmark is later consumed as a
CppPkg-native dep, `${pin.self.requested}` (reserved, Q2) upgrades this to
the exact consumer-requested ref — the fact that survives `.git`
stripping. No command execution in either mode.

**ninja (browse).** Before: pin.sh pre-generates `gen/build/browse_py.h`
with the upstream command; goes stale silently when `browse.py` is edited;
`includes = { private = ["gen"] }`. After: the `[generate.browse-py-h]`
stanza in §2.1, `includes = { private = ["${gen}"] }`, pin.sh block
deleted; edits to `browse.py` or `inline.sh` rebuild the header and its
one consumer (`browse.cc`) via depfile. **ninja (re2c)**, currently
dodged: expressible as two `checked-in` steps (`command = ["re2c", ...]`,
`checked-in = "src/lexer.cc"`), giving upstream's exact
"committed-output, regenerate via explicit action" contract with
`cpp-pkg gen --check` as the drift guard; builds never require re2c.

**vtz (zic pipeline).** Honest split. The pinned tzdb *fetch*
(`.tar.lz` + cldr commit pin) is tier d — stays in
`scripts/fetch-tzdata.sh` (§6). Given the fetched tree, the zic edge is
tier b:

```toml
[generate.zoneinfo]
command     = ["zic", "-b", "fat", "-d", "${gen}/zoneinfo",
               "data/tzdata/tzdata.zi"]
inputs      = ["data/tzdata/tzdata.zi"]
output-dirs = ["zoneinfo"]
```

`${gen}/zoneinfo` is a *test fixture*, referenced from B2 run-config
(`env = { VTZ_TZDATA_PATH = "${gen}/zoneinfo" }`), so by §1.3 laziness it
runs only for `cpp-pkg test`. The two checked-in headers
(`known_zones.h`, `embedded_tzdb_content.h`) become `checked-in` steps
(§2.1) — replacing the hand-rolled `--verify-refresh` with
`cpp-pkg gen --check`, already proven byte-identical against tzdb 2026a.

### 2.4 Implementation sketch

- `src/interp.rs` (new): the `${...}` resolver — closed vocabulary,
  position whitelist, `$${` escape; consumes `PackageMeta` + `Lockfile`.
- `src/schema.rs`: `RawGenerate` → `GenerateSpec` (enum `Template {..} |
  Command {..}`), validation (tier exclusivity, path rules, charset).
- `src/generate.rs` (new): tier-a rendering (tokenize `@VAR@`, §1.6
  errors, write-if-changed); tier-b edge construction; output-collision
  and `${gen}`-reference checks; `checked-in` copy/diff logic.
- `src/graph.rs`: resolve `${gen}` in `includes`/`sources`
  (`expand_sources` learns declared-output matching); mark plans that
  reference `${gen}` for phony wiring; laziness by requested-set scan.
- `src/ninja_gen.rs`: emit one rule per command step (via
  `cpp-pkg gen-exec` wrapper), `restat = 1`, stamp files for
  `output-dirs`, phony `cppkg-gen`, order-only deps on marked units.
- `src/cli.rs`: `gen` verb (`--check`, default = refresh); `gen-exec`
  hidden verb (sandbox wrapper, §1.4).
- `src/hashing.rs`: no v1 change (deps are CMake-built); doc note for B6.

Estimated: interp + template tier are small and pure (unit-testable
without a toolchain); the wrapper + sandbox is the only platform-touching
code.

### 2.5 Costs (honest)

- Two mechanisms in one table — the `template`/`command` discrimination is
  a mild "two special cases" smell against charter tie-breaker 3. Defense:
  the tiers have genuinely different hermeticity classes (pure function
  vs. sandboxed command), and collapsing them (Candidate 3) makes the
  common case worse.
- `${...}` is a new grammar element and a permanent scope-creep magnet;
  the closed vocabulary + position whitelist is the containment, and every
  future addition is a schema change to be argued, not a drive-by.
- `checked-in` adds a verb (`cpp-pkg gen`) and a third step flavor —
  droppable without harming the core (Q4).
- Coarse `${gen}` wiring: any gen-output change may first-build-order
  against all `${gen}`-referencing units (precision returns via depfiles
  from build 2). Harmless at corpus scale; Q3 covers the finer grain.
- Host tools unhashed (§1.4); macOS network enforcement best-effort.

## 3. Candidate 2 — target-attached tier a, package-level tier b

The cpptrace GAPS strawman, completed: `configure_file`-class generation
is declared *on the consuming target*, keyed by output path, and the
include wiring is automatic; commands stay package-level as in Candidate 1.

### 3.1 TOML surface

```toml
[targets.cpptrace.generate."include/cpptrace/version.hpp"]
template   = "cmake/in/version-hpp.in"
vars       = { CPPTRACE_VERSION_MAJOR = "${package.version.major}", ... }
visibility = "public"          # default "private"

# tier b unchanged from Candidate 1:
[generate.browse-py-h]
command = ["sh", "src/inline.sh", "kBrowsePy"]
# ...
```

Semantics: output lands at `${gen}/<target>/<output-path>`; the directory
prefix needed to make `#include <cpptrace/version.hpp>` resolve is
computed from the output key and added to the target's includes at the
declared visibility. No `${gen}` token appears for tier a at all.

### 3.2 Corpus rewrites

- **cpptrace**: the stanza above; `includes` shrinks back to upstream's
  `{ public = ["include"], private = ["src"] }` — the generated dir is
  invisible plumbing. *Most elegant single rewrite of any candidate.*
- **json-tui**: `[targets.json-tui-lib.generate."version.hpp"]` — but the
  `tests` target **also** compiles sources that include it (both targets
  list `gen/src` today). Either the stanza is duplicated per target (two
  substitutions of the same template — drift-prone, the exact disease
  this design treats) or a sharing rule is invented ("a target may
  reference another target's generated output"), which reintroduces
  cross-target wiring with worse spelling than `${gen}`.
- **benchmark**: identical to Candidate 1 (interpolated define; no step).
- **ninja / vtz**: identical to Candidate 1 (tier b / checked-in are
  package-level either way).

### 3.3 Costs

- Two *homes* for generation (target sub-table for templates, package
  table for commands) — a reader must know which tier lives where. This
  is a worse split than Candidate 1's two-keys-one-table: it splits by
  location, not just by field.
- The multi-consumer case (json-tui — 1 of the 2 template corpus sites!)
  is strictly worse. The "one target owns it" assumption fails at 50% in
  a 2-site corpus.
- Quoted-path table keys (`generate."include/cpptrace/version.hpp"`) are
  unlike every other key in the schema (charset-restricted names
  everywhere else).
- Automatic include-dir computation is magic — the declarative reading of
  `includes` no longer states all include roots (charter tie-breaker 1
  bruise).
- Implementation: same modules as Candidate 1 plus per-target output
  namespacing; slightly more graph plumbing, no savings.

Kept as a real candidate because its best case (cpptrace) is genuinely
the prettiest TOML in this file, and the taste judge should see what is
being given up by rejecting it.

## 4. Candidate 3 — one mechanism: commands only (S4-B, completed)

Tier a is expressed through the command tier: cpp-pkg ships a hermetic
builtin subcommand, so there is exactly one `[generate]` shape.

### 4.1 TOML surface

```toml
[generate.version-header]
command = ["cpp-pkg", "substitute", "src/version.hpp.in",
           "--var", "CMAKE_PROJECT_VERSION=${package.version}"]
stdout  = "src/version.hpp"
inputs  = ["src/version.hpp.in"]
```

`cpp-pkg substitute` implements §1.6 exactly; the wrapper recognizes the
builtin and runs it in-process (no PATH dependence, no sandbox needed for
it).

### 4.2 Corpus rewrites

json-tui/cpptrace become 5-line command stanzas like the above (inputs
now declared by hand — forgettable, whereas Candidate 1's `template` key
hashes itself). benchmark: unchanged (interpolated define — note that
`${...}` interpolation is needed by *every* candidate; single-mechanism
purity does not remove the grammar). ninja/vtz: identical to Candidate 1.

### 4.3 Costs

- The most common pattern in the wild (both GAPS files say so) gets the
  most verbose, least declarative spelling; a version header reads like a
  shell invocation.
- Hermeticity of templates is now claimed-by-convention (argv happens to
  start with `cpp-pkg substitute`) instead of guaranteed-by-construction;
  a future B6 config-hash rule and any static analysis must special-case
  the builtin anyway — the "one mechanism" is one only in syntax.
- Self-referencing the tool by name in manifests is ugly and versions
  badly (manifest meaning depends on the cpp-pkg binary's subcommand
  contract).
- Pro, honestly stated: smallest schema (no `template`/`vars`/`output`
  keys), one code path in ninja_gen, and the model never needs a "which
  tier is this" question. If the taste judge weighs schema size above
  common-case ergonomics, this is defensible — the corpus says it is the
  wrong trade (4 of 6 codegen sites are template-shaped).

## 5. Interaction analysis (flags × cfg × codegen × tests, plus B5/B6/B9)

- **B1 flags (S1)**: generated units compile with the owning target's
  flags — no special case. `${gen}` include roots are project-owned →
  `-I`, never `-isystem` (the `-isystem` fix targets *imported*
  interfaces only; a project's own generated header tripping its own
  `-Werror` is a bug the author should see). **Coupling to flag it**: S1
  deferred per-source flags *because* B4 subsumes the wave-1 cases; that
  is only true if interpolated `defines` (§1.1) land. If the taste judge
  rejects interpolation-in-defines, benchmark's per-source version define
  falls back into S1's court — the two decisions must be made together.
- **B3 cfg (S3)**: v1 `[generate]` steps are unconditional (no corpus
  site conditions a step on platform). cfg-selected *sources* may
  reference `${gen}` freely. When a need appears, whichever S3 surface
  wins is adopted verbatim on `[generate.*]` tables (cfg sub-tables merge
  by field / `when` per entry) — no new grammar invented here. One rule
  decided now: a step whose outputs are referenced only from inactive cfg
  branches does not run (laziness §1.3 already gives this, since inactive
  branches leave the requested closure).
- **B2 tests**: two touchpoints. (1) Fixtures: test run-config
  (`args`/`cwd`/`env`) may interpolate `${gen}` — vtz's zoneinfo is the
  proving case; this is B4 handing B2 its fixture-provisioning hook
  rather than B2 growing a parallel one (charter: one orthogonal
  primitive). (2) Laziness: with tests out of the default build,
  fixture-only steps run only under `cpp-pkg test` — no dev-only marker
  needed on steps.
- **B6 install/export**: cpptrace's generated `version.hpp` is a
  **public** include. The round-trip exporter must stage `${gen}` public
  include roots into the installed prefix exactly like source include
  roots — B6's design must treat "include root" as (path, provenance)
  where provenance ∈ {source, gen}. Flagged to the B6 designer.
- **B5 patches**: none direct. `${pin.<dep>.commit}` reads the lockfile;
  a patched dep's `commit` is the base commit (patch bytes are config-hash
  input, not a pin fact). No new variable needed.
- **B9 target-defaults**: `${gen}` tokens are legal in defaults tables
  like any include/define value; interpolation happens after defaults
  merge (so `${gen}` in a default means each target's ordinary gen root —
  identical for all, no ambiguity in v1's single-root model).
- **B7 hermeticity scan**: gen commands run sandboxed (§1.4); the
  store-manifest absolute-path scan is unaffected because `${gen}` lives
  under `build/` and never enters store manifests until B6, where it is
  exported by staging (relative), not by path.

## 6. Why tiers (c) and (d) stay deferred

- **Tier c — per-source transform over a glob** (cppcheck matchcompiler,
  1/8 projects): needs three new concepts at once — command *templates*
  with `{input}`/`{output}` holes, glob→output-name mapping, and
  source-list *replacement* (compile `mc_X.cpp` instead of `X.cpp`).
  Each is a real design decision with zero second data points, and the
  workaround (`USE_MATCHCOMPILER=Off`) is behavior-identical *by
  upstream's own contract* (it ships a Verify mode asserting exactly
  that). Wait for the protobuf/ICU-class migration; design it then with
  two corpus points instead of one. What is decided now so tier c stays
  additive: step names and `${gen}` layout leave room for
  `[generate.mc]`-style steps producing *sets* of outputs.
- **Tier d — pinned asset fetch+extract** (vtz, 1/8): network by nature,
  so it can never be a tier-b edge (§1.4's no-network contract is load-
  bearing); `.tar.lz` needs libarchive-class extraction; and the vtz case
  is half test-fixture provisioning (B2's territory) — the fetched tree
  feeds zic, whose *output* is a fixture, not a compile input. The
  BACKLOG's `[assets]` strawman stays a strawman until a second project
  needs it. Interim contract, stated in docs: pinned fetch lives in a
  script; `[generate]` inputs that don't exist yield a hard error naming
  the missing path (§2.2) so the script dependency is at least loud.

## 7. Linux story (explicit, per the campaign gate)

- **Tier a** is pure Rust string processing — bit-identical across
  platforms by construction; no shell, no tools.
- **Tier b** argv edges run identically under ninja on Linux; corpus
  commands (`sh`, `python3`, `zic`) are all present on Arch base +
  `tzdata`/`python` packages; nothing in the design shells through
  macOS-specific tooling (the `cmake -E tar` dependency belongs to
  deferred tier d).
- **Sandboxing is *stronger* on Linux**: `unshare -n` (user+net
  namespaces, unprivileged, default-enabled on Arch kernels) gives
  enforced no-network; macOS remains best-effort `sandbox-exec`. The
  contract is identical on both; Linux is where it is provable.
- **Case sensitivity**: output-collision checks are case-insensitive on
  both platforms (§1.2), so a manifest authored on macOS cannot mean two
  distinct files on Linux.
- gcc 16 / clang 22: gen edges don't touch the compiler; depfile-based
  precision (§1.3) uses `-MD` which both emit identically.
- Nothing in `[generate]` encodes platform truth, so the same stanzas are
  correct on both OSes — codegen adds **zero** new macOS-projection
  surface (the cfg problem stays B3's, not B4's).

## 8. Recommendation

**Candidate 1**, with `checked-in` mode included (Q4 asks the judge to
confirm). It refines the BACKLOG's already-picked shape rather than
reinventing; it covers 6/6 exercised corpus sites (2 fully dissolved by
tier a, 1 by interpolated defines alone, 2 by tier b, vtz split honestly
across tier b + checked-in + deferred tier d); its two tiers correspond to
two *real* hermeticity classes, which Candidate 3 erases syntactically but
not semantically; and it survives the multi-consumer case that kills
Candidate 2's prettiest feature.

## OPEN QUESTIONS for the taste judge

1. **Interpolation in `defines` values** (benchmark's whole fix): accept
   `${...}` in target `defines` — or is that grammar leaking out of
   `[generate]`? If rejected, per-source defines return to S1's scope and
   benchmark keeps its drift hazard. (Recommended: accept; the vocabulary
   and position whitelist are the containment.)
2. **`${pin.self.*}` root-build semantics** (reserved either way): when
   the package is the root project with no lockfile entry for itself —
   (a) hard error ("only meaningful as a dependency"), (b) derive from
   `git describe`/`rev-parse` when `.git` exists (deterministic per
   checkout, but reintroduces exactly the tool-execution class the tier
   exists to avoid), or (c) synthesize from `[package].version`
   (`tag:v<version>`) — silent-fallback-shaped, benchmark's original
   trap. (Weak recommendation: (a); manifests use `${package.version}`
   in root-visible positions.)
3. **Gen-root granularity**: single `${gen}` (recommended v1; coarse
   first-build ordering, coarse laziness) vs per-step `${gen.<name>}`
   (precise, but every reference names a step and renames ripple). Is
   coarse acceptable until a corpus site proves otherwise?
4. **`checked-in` + `cpp-pkg gen` verb in v1?** It covers vtz's two
   headers and ninja's re2c contract and blesses the
   checked-in-generated pattern the vtz GAPS asks to bless — at the cost
   of a verb and a third step flavor. Drop it and those two sites keep
   script workarounds (both currently *working*).
5. **Spelling**: `[generate]` vs `[codegen]`; `template`/`vars`/`output`
   vs a `configure-file`-echoing name; `@VAR@`-only vs also `${VAR}` in
   templates. (Recommended as written; `@VAR@`-only matches the corpus's
   `.in` files and keeps one interpolation grammar for manifests only.)
6. **`#cmakedefine` hard error** acceptable for v1 (no corpus need), or
   implement `#cmakedefine`/`01` now to widen tier a's real-world reach?
7. **Sandbox posture**: is "enforced on Linux, best-effort on macOS,
   normative contract on both" acceptable, or must v1 ship
   policy-documentation-only (no wrapper) / hard-require enforcement
   everywhere?
8. **Tier-a execution point**: generation-time write-if-changed leans on
   v0's "regenerate build.ninja every build". If that contract is ever
   relaxed, templates must become (builtin) ninja edges — accept the
   lean now, or emit them as edges from day one (Candidate 3's one good
   idea, applicable inside Candidate 1)?
