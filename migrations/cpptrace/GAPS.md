# GAPS — cpptrace migration

Everything that rubbed, keyed to the design-question lens. Overall: the core
worked shockingly well — first `cpp-pkg build` of the finished manifest
succeeded end-to-end, and PRIVATE static-lib dep semantics (LINK_ONLY) are
exactly right. The gaps are around the edges of the build, not the middle.

## dep-provisioning

### 1. No way to point a dependency at a CMakeLists in a subdirectory (major)

zstd is the canonical case: `facebook/zstd`'s `CMakeLists.txt` lives in
`build/cmake/`, both in the git repo and in the release tarball upstream
FetchContent-pins (FetchContent has `SOURCE_SUBDIR` for exactly this).
Declared attempt:

```toml
[dependencies.zstd]
git = "https://github.com/facebook/zstd"
tag = "v1.5.7"
```

fails at configure with:

> CMake Error: The source directory ".../raw/zstd-f8745da6ff1ad1e7" does not
> appear to contain CMakeLists.txt.

What's needed: a `subdir = "build/cmake"` field on the dependency (valid for
both `git` and `url` forms), folded into the config hash. This is the single
missing piece for the declared-dep route here; everything downstream
(libdwarf's `find_package(zstd)` via `needs = ["zstd"]`) would then
compose. No url-tarball workaround exists — the official release tarball has
the same layout, and there is no cmake-at-root zstd release artifact.

### 2. System/Homebrew libraries silently leak into store artifacts (major)

Experiment: building libdwarf with `ENABLE_DECOMPRESSION=TRUE` (upstream's
effective default) **succeeds** — its `find_package(ZLIB)`/`find_package(zstd)`
resolve to the macOS SDK `libz.tbd` and Homebrew's
`/opt/homebrew/lib/libzstd.dylib`, the probe faithfully extracts
`ZLIB::ZLIB` / `ZSTD::ZSTD` with those absolute paths into the manifest,
LINK_ONLY propagation works, and the demo ends up linked against
`/opt/homebrew/opt/zstd/lib/libzstd.1.dylib`. Nothing warned.

Two problems: (a) the store entry is machine-dependent (hard-coded Homebrew
paths, Homebrew zstd version) while its config hash says nothing about the
system libs — two machines produce different artifacts under the same key;
(b) the user never *declared* an intent to use a system library. What's
needed: a first-class system-dependency declaration (e.g.
`zstd = { system = true }` resolving via pkg-config/SDK with the resolved
identity folded into the hash), plus a hermeticity policy for undeclared
absolute paths escaping into manifests (warn or error). The scan that exists
today (find-registry off + CMakeCache leak scan) did not catch this.

Chosen fallback for the migration: `ENABLE_DECOMPRESSION=FALSE` — hermetic,
and a no-op for Mach-O (compressed debug sections are an ELF feature). This
is a real scope reduction on other platforms: a Linux build of this manifest
would silently lose compressed-`.debug_*` support.

### 3. What went right (worth keeping)

libdwarf-lite is properly installable and its `install(EXPORT)` produces the
real imported target `libdwarf::dwarf` — the tier-2 probe extracted it with
its public defines (`LIBDWARF_STATIC`, `PIC`) and flat headers, first try.
Note the trap the probe sidesteps: the in-build ALIAS names
(`libdwarf::dwarf-static`, what upstream links under FetchContent) do not
exist in the installed config — cpptrace's own CMake carries a 4-branch
`if(TARGET ...)` ladder for this; with cpp-pkg the store manifest is the
single source of truth and the right name is discoverable.

## codegen-escape-hatch

### 4. `configure_file` version header, pre-generated by pin.sh (minor here, major in general)

Upstream: `configure_file(cmake/in/version-hpp.in
${PROJECT_BINARY_DIR}/include/cpptrace/version.hpp)` + that dir as a public
include. Workaround: `pin.sh` substitutes the three `@VARS@` with `sed` into
`gen/include/cpptrace/version.hpp` in the *source tree*, and the manifest
exposes `gen/include` publicly. Cost: source tree pollution, and the
version is now stated in three places (upstream template consts, pin.sh sed
args, `[package] version`).

What a native escape hatch needed to do here — deliberately tiny:

```toml
[targets.cpptrace.generate."include/cpptrace/version.hpp"]
template = "cmake/in/version-hpp.in"          # @VAR@ substitution
vars = { CPPTRACE_VERSION_MAJOR = "1", ... }  # or derive from package.version
```

outputs under `build/gen/`, auto-added to the target's includes with the
declared visibility, hashed as inputs. This covers the whole
`configure_file` class (by far the most common codegen in the wild) without
opening the arbitrary-command box. cpptrace needs nothing fancier.

## conditional-sources

### 5. Compile-probe results and platform defines have no home (major)

cpptrace's *sources* are unconditional (all back-ends always compile — the
project was practically designed for dumb build systems). But its *defines*
are the output of ~8 `check_cxx_source_compiles` probes plus an
OS/compiler decision tree (`cmake/Autoconfig.cmake`). The manifest bakes in
the macOS/Apple-clang answers (verified against the upstream ninja
`DEFINES =` line), which means:

- this `CppPkg.toml` is **platform-specific**; a Linux port needs a
  different define set (`CPPTRACE_UNWIND_WITH_UNWIND`, `HAS_DL_FIND_OBJECT`,
  ...) and there is no `[targets.x.'cfg(linux)']`-style conditional in the
  schema, and
- there is no `has_include`/try-compile primitive to regenerate those
  answers, so ports are done by reading the upstream autoconfig by hand.

For v0 this was a perfectly workable workaround (the comment block in
CppPkg.toml documents the derivation). For the design: platform-conditional
defines/sources (cfg-style, cargo-familiar) are the 90% need; a
try-compile escape hatch is the 10%.

## per-target-flags

### 6. No per-target compile options; profiles are the only flag surface (major)

Upstream puts `-fvisibility=hidden -fvisibility-inlines-hidden` and
`-Wall -Wextra -Werror=return-type -Wundef` on the library target only.
v0 schema has no `cxx-flags` on targets, so these ride on
`[profiles.relwithdebinfo]` and hit every project target (demo included —
harmless here, wrong in general: a vendored-in-tree third-party target
would suddenly get your -Werror). Two sub-issues:

- **granularity**: flags cannot be scoped to a target; and
- **duplication**: profile flags must be repeated per profile — supporting
  all four configs means four copies of the same warning block. A
  profile-independent layer (`[flags]` project-wide, `cxx-flags` per
  target) would fix both.

### 7. `cxx-extensions` reserved-but-absent shows up in practice (minor)

Upstream compiles at the compiler default (`gnu++17`); cpp-pkg emits strict
`-std=c++17`. cpptrace is clean C++ so the only observable delta was one
extra `std::__1::piecewise_construct` symbol in the archive, but a project
using GNU extensions would need the reserved `cxx-extensions = true` today.

## testing-story

### 8. Tests were not portable, and cpp-pkg has no test concept (major)

Upstream's suite (`CPPTRACE_BUILD_TESTING`) is: gtest via FetchContent (or
`CPPTRACE_USE_EXTERNAL_GTEST`), per-test targets with per-target `-g`/split
-dwarf/dwarf-version knobs, CTest registration, plus integration/signal
demos. None of this maps: no test target kind, no test-only dependencies
(gtest would become an unconditional `[dependencies]` entry built into the
regular graph), no `cpp-pkg test` runner, no expected-output harness. The
migration reduces "testing" to building/running `test/demo.cpp` as an
ordinary executable — that is a genuine scope reduction (the unit suite was
not ported). Minimum viable story a cargo user expects: `[targets.x] type =
"test"` implying (a) dev-dependency visibility, (b) excluded from default
build, (c) run+aggregated by `cpp-pkg test`.

## install-export

### 9. cpp-pkg can build a library package but not publish one (major)

cpptrace exists to be consumed: upstream installs headers + generated
`version.hpp` + `libcpptrace.a`, a hand-written `cpptrace-config.cmake`, a
version file with SameMajorVersion semantics, and (FetchContent mode) even
bundles `libdwarf.a`/`libzstd.a` + their headers into its own prefix so the
static link closure survives installation. The cpp-pkg migration produces
`libcpptrace.a` in `build/` and stops — there is no `cpp-pkg install`, no
prefix layout, no emission of a config/CPS for *this project's* targets
(the shim emitter exists for dependencies; pointing the same machinery at
the project's own manifest is the natural fix). Until then a migrated
library is a dead end for non-cpp-pkg consumers, which for a library author
is disqualifying. The transitive-closure question upstream answers by
vendoring (`libdwarf.a` copied into the prefix) needs an explicit design:
install dep artifacts, or emit requires on store paths.

## object-libraries

Not exercised: cpptrace uses no OBJECT libraries. No data from this
migration.

## schema-ergonomics

### 10. Small stuff (minor)

- `sources = ["src/**/*.cpp"]` matching files at every depth including
  `src/*.cpp` directly: correct and pleasant — replaced upstream's 45-line
  hand-maintained list. Verified equal (45 members in both archives).
- Build outputs land flat in `./build` regardless of `--config`; switching
  configs recompiles in place. Per-config output dirs
  (`build/relwithdebinfo/`) would match user expectation (CMake and cargo
  both separate).
- Option values are literal strings (`"TRUE"`/`"OFF"`): fine, but migrating
  from CMake means faithfully copying upstream's spelling; a lint that
  flags `options` keys the dep's cache never declared would catch typos
  (misspelled `ENABLE_DECOMPRESSION` would today just silently rebuild with
  the default).
- The `[dependencies.libdwarf.options]` + comment-heavy manifest reads
  well; total manifest is ~100 lines (vs ~950 upstream incl. autoconfig) —
  the density win is real, the platform-specificity (gap 5) is what it
  cost.
