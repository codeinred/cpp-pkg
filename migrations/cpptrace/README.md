# Migration: cpptrace v1.0.4

- Upstream: https://github.com/jeremy-rifkin/cpptrace
- Ref: tag `v1.0.4` = commit `3db8da80111171c219ab5839905771386bee06b3`
- Platform exercised: macOS arm64, Apple clang 21, `relwithdebinfo`
- Status: **green** — full parity on the demo protocol, no source patches.

## What the project is

cpptrace is a portable C++11 stacktrace library. Its upstream build is a
573-line `CMakeLists.txt` plus a compile-probe autoconfig layer
(`cmake/Autoconfig.cmake`) that picks unwinding/symbol/demangle back-ends per
platform, a `configure_file`-generated `version.hpp`, and — the interesting
part for cpp-pkg — **FetchContent-vendored dependencies**: libdwarf (the
`jeremy-rifkin/libdwarf-lite` fork, pinned by commit) and zstd (URL tarball
whose `CMakeLists.txt` lives in `build/cmake/`).

Nice structural property: cpptrace compiles **all** back-end sources on all
platforms (`symbols_with_dbghelp.cpp` etc. become empty TUs when their define
is absent), so the source list is unconditional — only the *defines* are
platform-dependent.

## Migration approach

- `CppPkg.toml` replaces the whole CMake build:
  - `[targets.cpptrace]` static library, `sources = ["src/**/*.cpp"]`
    (resolves to exactly the 45 files upstream lists), public `include/` +
    generated `gen/include/`, private `src/`.
  - The macOS results of upstream's compile probes are baked in as private
    defines (`CPPTRACE_UNWIND_WITH_EXECINFO`,
    `CPPTRACE_GET_SYMBOLS_WITH_LIBDWARF`, `CPPTRACE_DEMANGLE_WITH_CXXABI`,
    `CPPTRACE_HAS_CXX_EXCEPTION_TYPE`, `CPPTRACE_HAS_MACH_VM`,
    `HAS_ATTRIBUTE_PACKED`, `NOMINMAX`), ground truth taken from an
    upstream ninja build's `DEFINES =` line.
  - `[targets.demo]` builds upstream's `test/demo.cpp` unmodified.
- **libdwarf became a declared dependency** instead of FetchContent: git dep
  on `libdwarf-lite` at the exact commit upstream pins
  (`CPPTRACE_LIBDWARF_TAG`). Its `install(EXPORT)` publishes the real
  imported target `libdwarf::dwarf`, which the tier-2 probe extracts
  cleanly (note: the in-build ALIAS `libdwarf::dwarf-static` that upstream
  links does not exist in the installed config). Declared PRIVATE on the
  cpptrace target, exactly like upstream.
- **zstd support was dropped** (`ENABLE_DECOMPRESSION=FALSE` on libdwarf).
  This is a deliberate, documented scope reduction: zstd cannot be a
  declared cpp-pkg dep (see GAPS.md dep-provisioning), and
  zstd/zlib-compressed debug sections are an ELF feature — Apple clang
  emits uncompressed Mach-O debug info, so the macOS demo behavior is
  unchanged. (A run with `ENABLE_DECOMPRESSION=TRUE` also fully works via
  Homebrew zstd, but bakes `/opt/homebrew` paths into the store — gap data,
  see GAPS.md.)
- `version.hpp` (upstream `configure_file`) is pre-generated by `pin.sh`
  with `sed` into `gen/include/cpptrace/version.hpp` (codegen escape-hatch
  workaround).
- Upstream's per-target warning/visibility flags ride on
  `[profiles.relwithdebinfo]` (no per-target flags in v0).
- Not ported (scope reduction, stated): the unit/integration test suite
  (gtest-entangled; see GAPS.md testing-story), the C `ctrace` demo, tools/,
  shared-library and module builds, and installing cpptrace itself as a
  package (cpp-pkg v0 cannot express installs; see GAPS.md install-export).

## Reproduce

```sh
cd migrations/cpptrace
./pin.sh                       # clones upstream at the pinned commit into ./upstream,
                               # generates gen/include/cpptrace/version.hpp,
                               # copies CppPkg.toml + CppPkg.lock in
cd upstream
CPPKG_STORE=/tmp/cpptrace-store cpp-pkg build --config relwithdebinfo
./build/demo
```

Second `cpp-pkg build` is a dependency store cache hit (no
"building dependency libdwarf" line; ninja reports no work).

## Parity evidence

Protocol: build the same `test/demo.cpp` (a) upstream: CMake+ninja
RelWithDebInfo build, `cmake --install`, tiny find_package consumer; (b)
cpp-pkg as above. Run both; normalize hex addresses, the staging path
prefix, and dyld's `start + N` offset; diff.

Result: **normalized outputs byte-identical** — 15/17-frame traces with
demangled template function names, inlined-frame attribution, and
`file:line:col` for every project frame, including the
`from_current_exception()` trace from the CPPTRACE_CATCH handler (and the
same two benign `[cpptrace error] Unable to read object file
/usr/lib/...dylib` lines for system frames on both sides). Symbolization
runs through libdwarf against the Mach-O debug map (.o files) — no dSYM
needed.

Archive parity: both `libcpptrace.a` contain 45 members; exported symbol
sets identical except one extra `std::__1::piecewise_construct` in the
cpp-pkg build (strict `-std=c++17` vs upstream's compiler-default
`gnu++17` — cosmetic).

Private-dep hygiene verified in `build/compile_commands.json` /
`build.ninja`: the demo TU sees no libdwarf include dirs and no
`LIBDWARF_STATIC` define, while `libdwarf.a` still reaches the final link
(static-library LINK_ONLY propagation).

## Files

- `CppPkg.toml` — the whole build (source of truth; pin.sh copies it in)
